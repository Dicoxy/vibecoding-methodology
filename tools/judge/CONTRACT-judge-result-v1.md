# CONTRACT — J1 · Судья результата (`judge.sh`)

```
Блок:        J1 — Судья результата
Статус:      draft
Стадия:      сборка (инструмент для продакшен-цикла MARS)
Исполнитель: Claude Code на русском сервере — НЕ конвейер MARS
Ветка:       tools/judge-v1 (от main, репозиторий методологии). В main не пушить.
Приёмка:     Гриша по результату калибровочного прогона (§6). Исполнитель приёмку не выносит.
Зависимости: доступ русского сервера к /opt/mars; node >= 20; jest установлен в api/
Проброс:     все недетерминированные входы — параметрами: путь к репозиторию,
             номер контракта, имя ветки, каталог worktree, каталог вердиктов,
             часы (timestamp вердикта). Значения по умолчанию допустимы,
             хардкод путей — нет.
Парный контракт: CC-014 (MARS) — первый контракт, судимый внешне
```

---

## §1 Зачем

В цикле MARS §4 «Приёмка» сегодня прогоняет сам исполнитель и сам же пишет
`CC-NNN-report.md`. Это отсутствие приёмки, оформленное как приёмка: оценивающий
заинтересован в оценке. J1 выносит вердикт вне ветки исполнителя и без его участия.

Наследует от GOAL A2 (судья стоит в цикле денежного проекта) и от §6 шаблона
CONTRACT («приёмку выполняет не исполнитель»).

J1 судит **исполнение**, а не текст контракта. Проверку самого контракта до старта
делает другой блок — Судья архитектуры (J2), он к этому контракту не относится.

**Разметка приёмок в закрытых циклах** (замер 16.09.2026): из 12 контрактов
машинно исполнимую команду в §4 содержат 9. Без неё — CC-001, CC-003, CC-006.
Это и есть калибровочный корпус: 9 годных, 3 за пределами области J1.

**Репозиторий методологии:** финский сервер, `/home/dev/vibecoding-methodology`,
публичное зеркало `github.com/Dicoxy/vibecoding-methodology`. Русский сервер
видит его по HTTPS (`git ls-remote` отвечает).

**Чего нет:**
- `judge.sh` не существует ни на одном сервере
- клона методологии на русском сервере нет
- CI нет: запуск judge — ручной или по крону, не по хуку
- `DEEPSEEK_API_KEY` есть только на финском сервере. J1 модель не вызывает вообще
- прод-БД MARS трогать нельзя; тесты работают на фикстурах

**Открытость кода судьи — принятый компромисс.** Репозиторий методологии публичный,
значит код J1 исполнителю доступен. Для судьи результата это не уязвимость:
он проверяет факт прогона, а не признаки в тексте. Знание его кода не делает
красные тесты зелёными. На J2 (LLM-судья архитектуры) это правило не переносится.

## §3 Вход

Два аргумента и машинный блок в контракте.

```
judge.sh --repo /opt/mars --contract CC-014 [--branch cc/014-slug]
```

Ветка по умолчанию выводится из `--contract` поиском `cc/NNN-*` среди remote-веток;
неоднозначность -> НЕПРИМЕНИМ, не угадывание.

Машинная часть приёмки живёт в самом контракте MARS — блок с языком `acceptance`
внутри §4. Пример реальный, для CC-013 он выглядел бы так:

````
```acceptance
workdir: api
tests: npx jest
max_failures: 0
max_total: 34
require_files:
  - docs/contracts/CC-013-report.md
manual:
  - живой прогон: POST /errands {destination:'Гриша'} -> COMPLETE -> робот на станции
```
````

Поля: `workdir` (каталог запуска, относительный), `tests` (команда),
`max_failures` (целое), `max_total` (целое, потолок числа тестов — защита
от «дописал зелёных и прошёл»), `require_files` (список путей),
`manual` (список человеческих проверок, судьёй не выполняемых).
Обязательны `tests` и `max_failures`. Прозу §4 судья не разбирает.

## §4 Выход и гарантии

```
Г1. Вердикт выносится в отдельном worktree, созданном из судимой ветки,
    вне /opt/mars и вне рабочих копий tracks.
    Проверка: файл вердикта содержит путь worktree и sha коммита;
              после прогона worktree удалён (git worktree list чист).

Г2. Вердикт бинарный и машиночитаемый: ПРИНЯТ / ОТКЛОНЁН / НЕПРИМЕНИМ.
    Проверка: exit code 0 / 1 / 2 соответственно; первая строка файла вердикта —
              одно из трёх слов.

Г3. Судья не изменяет состояние MARS: ни рабочую копию, ни ветки, ни main.
    Проверка: `git status --porcelain` в /opt/mars до и после — идентичен;
              sha судимой ветки до и после — идентичен; в репозитории нет следов
              судьи, кроме создания и удаления worktree.

Г4. Контракт без блока acceptance -> НЕПРИМЕНИМ. Никогда не ПРИНЯТ.
    Проверка: CC-006 (блока нет) -> exit 2.

Г5. Ручные пункты не засчитываются автоматически. Вердикт ПРИНЯТ при непустом
    manual помечается «ПРИНЯТ (машинная часть), ручная часть не выполнена»
    и перечисляет пункты.
    Проверка: контракт с manual -> строка о ручной части присутствует в вердикте.

Г6. Превышение max_total -> ОТКЛОНЁН, даже если все тесты зелёные.
    Проверка: мутант M4 (§6) -> exit 1 с причиной «число тестов выше потолка».

Г7. Вердикт пишется вне репозитория MARS: в каталог вердиктов
    (по умолчанию /opt/judge/verdicts/CC-NNN-verdict-<timestamp>.md).
    Проверка: после прогона `git status` в /opt/mars чист (следствие Г3).
```

Перенос вердикта в `docs/contracts/` — действие оркестратора, не судьи.

## §5 Чего блок НЕ делает

- не судит текст контракта на противоречивость, полноту, соответствие цели —
  это J2, отдельный блок
- не вызывает LLM, не ходит в сеть, кроме `git fetch` в пределах origin MARS
- не чинит тесты, не коммитит, не мержит, не пушит, не переключает ветки
  в рабочих копиях
- не выполняет и не имитирует пункты `manual`
- не трогает `main`, `track/*`, прод-БД, файлы вне своего worktree и каталога вердиктов
- не выносит вердикт по контракту, вернувшему СТАТУС: НЕИСПОЛНИМО (§7 шаблона):
  такой возврат адресован оркестратору

## §6 Приёмка

Выполняет Гриша. Исполнитель прикладывает материалы, вердикт не выносит.

**Шаг 1 — ретро-разметка корпуса.** В 9 закрытых контрактах (CC-004, 005, 007,
008, 009, 010, 011, 012, 013) дописать блок `acceptance` по тому, что уже написано
в их §4 прозой. Ничего не додумывать: если в §4 нет числа — не изобретать число.
Побочный результат шага — ответ на вопрос, покрывает ли формат блока реальное
разнообразие приёмок MARS. Расхождения записать.

**Шаг 2 — калибровка на чистых.** Прогон J1 по всем 9. Ожидание: ни одного
ОТКЛОНЁН. Каждый ОТКЛОНЁН разбирается: либо баг судьи, либо находка —
цикл, который в своё время приняли зря.

**Шаг 3 — мутационный тест (04-validation §4.13).** Пять мутантов из копии
CC-013 в отдельной ветке:

```
M1  сломанный тест в api/            -> ОТКЛОНЁН (провал теста)
M2  отсутствует CC-013-report.md     -> ОТКЛОНЁН (require_files)
M3  блок acceptance удалён           -> НЕПРИМЕНИМ (Г4), не ПРИНЯТ
M4  дописаны зелёные тесты сверх 34  -> ОТКЛОНЁН (Г6)
M5  ветка cc/013 не от main          -> ОТКЛОНЁН (расхождение базы)
```

**Критерий допуска:** 5 из 5 мутантов пойманы, ни один из 9 чистых не отвергнут,
Г3 выполнена на каждом прогоне. Ниже — J1 в цикл не ставится.

**Шаг 4 — боевой.** CC-014 пишется с блоком `acceptance` и строкой:
«приёмку выносит judge.sh; отчёт исполнителя приёмкой не является».

## §7 Отказ по неисполнимости

```
СТАТУС:    НЕИСПОЛНИМО
ПРИЧИНА:   что недоступно или противоречиво
ЧТО НУЖНО: какое условие снимет блокировку
```

Адресовано оркестратору (среда, права) или архитектору (противоречие в контракте).
Молчание и имитация результата — брак.

## §8 Отчёт исполнения

По каждому пункту §3–§4: что сделано, какие файлы затронуты, коммиты, что осталось.
Отдельно — материалы калибровки: таблица 9 чистых прогонов, таблица 5 мутантов,
список расхождений из шага 1. Отчёт — свидетельство исполнителя, не приёмка.
