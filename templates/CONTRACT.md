# CONTRACT — шаблон

*Версия 1.1 | 6 сентября 2026*

**Происхождение.** Собран из двух обкатанных практик, не выдуман: формат MARS
(`docs/contracts/`, 44 волны с апреля 2026, CONTRACT_GUIDE v1.0) и контракт
`page-assembler` первого методологического цикла (10.08.2026). Всё, что ниже,
хотя бы раз выдержало столкновение с исполнителем.

**Что такое контракт.** Не задача («сделай X»), а интерфейс: вот что есть,
вот что должно получиться, вот что не трогать, вот как проверю. Исполнитель
получает контракт и не получает ничего сверх него — ни соседних блоков,
ни бизнес-контекста, ни кода Судьи.

**Правило языка.** Язык и технология реализации в контракте НЕ называются,
если они не являются частью требования. В первом цикле исполнитель сам выбрал
Python — это и есть проверка runtime-agnostic-тезиса. Называй язык только
тогда, когда блок обязан жить в конкретном рантайме, и тогда пиши это в §2
как факт окружения, а не как указание.

## Шапка

```
Блок:        номер и название
Статус:      draft / ratified <дата> (ratified = прошёл Судью архитектуры)
Стадия:      R&D / сборка / продакшен   ← определяет применимость критериев
Исполнитель: кто/что исполняет (агент, модель, человек)
Ветка:       cc/NNN-slug (от main). В main НЕ пушить.
Приёмка:     кто выносит вердикт (обязательно НЕ исполнитель)
Зависимости: что должно быть готово до старта
Проброс:     контролируемые входы (часы, random, id, env), которые блок принимает
             параметром — и которые ОБЯЗАНЫ принимать все блоки ниже по цепочке
Парный контракт: если блок стыкуется с соседним — какой и по каким полям
```

---

## §1 Зачем

Одна-две фразы: какую дыру закрывает блок и от какой части GOAL наследует
смысл. Не «что делает» — «зачем существует». Если написать не получается,
блок, скорее всего, не нужен.

## §2 Факты окружения (не выдумывай свои)

Состояние мира на момент старта: пути, ветки, версии, установленные пакеты,
команды запуска тестов, схема БД, доступные и недоступные ресурсы. С реальными
значениями, не с описаниями.

Отдельно и явно — **чего нет**: «прода и боевой БД нет», «lighthouse
в окружении не установлен». Исполнитель, не знающий об отсутствии, потратит
на это ходы и деньги.

> Проверка доступности исполнителя (авторизация, права, пробный запуск)
> делается ДО передачи контракта. План, опирающийся на непроверенное
> предположение о состоянии мира, — тот же мёртвый источник
> (04-validation.md, 4.10 и 4.14).

## §3 Вход

Формат, типы, ограничения, пример с реальными данными. Не «некий объект
с полем X», а конкретный JSON, который действительно приходит.

## §4 Выход и гарантии

Список пронумерованных гарантий. Каждая — проверяемое утверждение
о результате, а не о процессе.

```
Г1. <гарантия>        Проверка: <чем именно проверяется>
Г2. ...
```

**Каждая гарантия обязана иметь способ проверки.** Гарантия без инструмента
проверки — брак вида «непроверяемость» (4.11). Если инструмента нет —
либо не включай гарантию, либо оформи waiver (см. ниже).

## §5 Чего блок НЕ делает

Границы ответственности: какие файлы не трогать, какие компоненты не менять,
какие API не вызывать, какие паттерны не применять, что не входит в задачу.

Секция обязательна и практически всегда самая ценная: без неё исполнитель
уходит в соседнюю зону и порождает конфликт с параллельной работой.

## §6 Приёмка

Конкретные шаги с конкретными данными, дающие бинарный ответ.

```
1. <команда или действие> → <ожидаемый результат>
2. ...
```

Не «проверь, что работает», а «`cd api && npx jest` — зелено»,
«CC1 402 → карточка приглушена, жёлтая полоса».

**Приёмку выполняет не исполнитель.** Исполнитель, проверяющий сам себя,
— это отсутствие приёмки, оформленное как приёмка. Судья результата
запускается вне рабочей ветки, его код исполнителю не показывается,
и до первого вердикта Судья проходит мутационный тест (4.13).

**Waiver с условием истечения** — для критериев, неприменимых сейчас:

```
КРИТЕРИЙ: что снимается
ПРИЧИНА:  почему сейчас неприменимо
УСЛОВИЕ:  что должно произойти, чтобы waiver истёк
```

## §7 Отказ по неисполнимости

Если контракт невозможно выполнить, исполнитель НЕ имитирует результат
и не молчит, а возвращает:

```
СТАТУС:   НЕИСПОЛНИМО
ПРИЧИНА:  что именно недоступно или противоречиво
ЧТО НУЖНО: какое условие снимет блокировку
```

Возврат адресован оркестратору (среда, права) или архитектору (противоречие
в контракте), но не Судье результата: вердикт по нему не выносится.
Без этого канала заблокированный исполнитель выглядит как неисправный блок
(04-validation.md, 4.14).

## §8 Отчёт исполнения

Что сделано по каждому пункту §3–§4, какие файлы затронуты, коммиты,
что осталось. Отчёт — не доказательство приёмки, а свидетельство исполнителя:
вердикт выносится отдельно.

## Перед отправкой: самопроверка контракта

Судья архитектуры проверяет четыре свойства (04-validation.md, 4.12):

- [ ] **Исполнимость** — выполнимо в описанных в §2 условиях
- [ ] **Непротиворечивость** — гарантии §4 не конфликтуют между собой и с §5
- [ ] **Проверяемость** — по каждой гарантии §4 есть шаг в §6, дающий бинарный ответ
- [ ] **Соответствие цели** — §1 связан с GOAL, а не только с ближайшим удобством

Пятый вид брака — **неполнота** (незаписанная гарантия) — автоматически
не ловится. Его ловит человеческая приёмка результата, обязательная даже
при вердикте ПРИНЯТ.

## Антипаттерны

| Плохо | Почему | Хорошо |
|---|---|---|
| «Сделай красиво» | Субъективно, сто интерпретаций | «opacity-60 если dim_card=true» |
| §5 не заполнен | Исполнитель уходит в чужую зону | «НЕ трогать: api.js, FreshnessBadge.jsx» |
| Пример без реальных данных | Формат угадывается → баги | JSON с настоящим ответом API |
| Абстрактная приёмка | «Проверь, что работает» ничего не проверяет | «CC1 402 → жёлтая полоса» |
| Гарантия без инструмента | Судья не может вынести вердикт | Waiver с условием истечения |
| Приёмку делает исполнитель | Оценивающий заинтересован в оценке | Судья вне ветки исполнителя |
| Контракт написан параллельно с фундаментом | Фундамент меняется → контракт устарел | Сначала API/данные, потом контракт |

## Приложение: проброс контролируемых входов (v1.1)

Если блок принимает недетерминированный источник параметром (`now`, генератор
случайности, генератор id, переменные окружения, внешний вызов) ради того, чтобы
его гарантии были проверяемы детерминированно — этого недостаточно. **Каждый
блок ниже по цепочке вызовов обязан принимать тот же источник параметром.**
Иначе гарантия верхнего блока непроверяема (брак вида 3, 04-validation §4.11):
её детерминизм зависит от того, что нижний блок не обещал.

Поэтому строка «Проброс» в шапке — обязательство в обе стороны: контракт верхнего
блока накладывает требование на контракт нижнего, и оно записывается в обоих.
Незаписанное для Судьи не существует.

Источник: StarKids, 06.09.2026 — контракт `core` требовал «часы — параметр now»,
`store` ставил `decided_at` своими часами; гарантия «день выдачи» не тестировалась,
пока `now` не пробросили в store. Замечено в исполнении, не на бумаге.
